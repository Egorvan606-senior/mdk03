# Инструкция по обновлению АРМ для системного администратора

**ИС «Умный кампус». Клиент Campus Operator · утилита campus-healthcheck 1.0**

Регламент и схема доставки: [docs/UPDATE_REGULATION.md](docs/UPDATE_REGULATION.md).

## 1. Состав утилиты

| Файл | Назначение |
|---|---|
| `campus-healthcheck.exe` | утилита обновления и проверки (.NET 8) |
| `healthcheck.json` | путь установки, ожидаемая версия, пороги задержек, таймауты, повторы |
| `reports\readiness_act_*.md / *.json` | акты готовности АРМ |
| `logs\healthcheck_ГГГГММДД.log` | журнал работы |
| `backups\backup_*.zip` | резервные копии до обновления |

## 2. Подготовка (до окна обновления)

1. Получите пакет версии из `\\campus-fs\updates\operator\2.4.0\` (папки `files\` и файл `manifest.json`).
2. Проверьте, что в `healthcheck.json` указаны `"ExpectedVersion": "2.4.0"` и верный `InstallDir`.
3. На боевых АРМ раздел `Emulators` должен быть выключен (`false`) — эмуляторы только для стенда.
4. Убедитесь, что АРМ входит в текущее кольцо раскатки (см. регламент, раздел 2).

## 3. Установка обновления

```bat
cd C:\ProgramData\Campus\healthcheck
campus-healthcheck update --package \\campus-fs\updates\operator\2.4.0
```

Утилита выполняет 6 шагов: проверка SHA-256 пакета → резервная копия → снимок данных →
установка → контроль целостности → Health Check. При критичном сбое откат выполняется
автоматически.

## 4. Проверка без установки

```bat
campus-healthcheck check
```

Цепочка проверок:

| Код | Проверка | Критичная | Порог |
|---|---|---|---|
| CFG | `appsettings.json` читается, есть 7 обязательных ключей | да | — |
| APP_VER | `version.json` = ожидаемая версия | да | — |
| LOCAL_DB | файл SQLite: сигнатура, размер страниц, не заблокирован | да | — |
| CENTRAL_DB | PostgreSQL отвечает на SSLRequest | да | 200 мс |
| API | `api.ipify.org` отвечает 200 и возвращает внешний IP АРМ | да | 1500 мс |
| READER | контроллер считывателя отвечает `OK` на `STATUS` | да | 150 мс |
| DISK | свободно не менее 500 МБ | нет | — |

Сетевые проверки повторяются до 3 раз (пауза 300 / 600 мс). Превышение порога задержки
переводит результат в WARN.

**Коды завершения** (для планировщика и скриптов):

| Код | Значение | Действие |
|---|---|---|
| 0 | АРМ готово | подписать акт |
| 2 | готово с замечаниями | допустить, создать задачу на устранение |
| 1 | не готово | не допускать АРМ, разобрать по журналу |
| 3 | не готово, выполнен откат | инцидент, остановить раскатку кольца |
| 4 | ошибка запуска (параметры, нет файлов) | проверить команду и `healthcheck.json` |

## 5. Ручной откат

См. [регламент, раздел 4](docs/UPDATE_REGULATION.md#4-план-безопасного-отката-rollback-plan):
закрыть клиент → распаковать последний `backup_*.zip` в каталог установки → `campus-healthcheck check`.

## 6. Подготовка пакета (для группы сопровождения)

```bat
campus-healthcheck manifest --package D:\build\operator\2.4.0 --version 2.4.0 --channel Stable
```

Команда пересчитывает SHA-256 всех файлов в `files\` и записывает `manifest.json`.
Любое изменение файла после этого приведёт к отказу в установке на шаге 1.

## 7. Испытательный стенд (папка `stand/`)

| Папка | Содержимое |
|---|---|
| `stand/arm` | АРМ версии 2.3.1: конфигурация, SQLite (300 пропусков, 500 проходов), кэш |
| `stand/packages/2.4.0` | корректный пакет новой версии |
| `stand/packages/2.4.0-damaged` | пакет с изменённым после сборки файлом (проверка отказа по SHA-256) |

Сценарии (из папки `src/Campus.HealthCheck`):

```bat
dotnet run -- check                                                    & rem АРМ 2.3.1: версия не та
dotnet run -- update --package ..\..\stand\packages\2.4.0-damaged       & rem пакет отклонён
dotnet run -- update --package ..\..\stand\packages\2.4.0               & rem штатное обновление
dotnet run -- update --package ..\..\stand\packages\2.4.0 --emulators db & rem считыватель отключён -> откат
```

Вернуть стенд в исходное состояние: `git checkout -- stand/arm`.
