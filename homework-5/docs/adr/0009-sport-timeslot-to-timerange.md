# ADR-0009. Хранение слота бронирования спорткомплекса как диапазона `timerange` вместо строки `TimeSlot`

* **Статус:** Принято (Accepted)
* **Дата:** 2026-10-23
* **Автор:** Иванов Е.М. (группа И14-23-9)
* **Задача:** CAMPUS-110
* **Связанные документы:** [CR-2026-110](../change-requests/CR-2026-110.md), [CHANGELOG](../../CHANGELOG.md)
* **Заменяет / заменено:** —

## Контекст

В модуле «Спортивный комплекс» слот бронирования зала хранится в колонке
`sport.bookings.time_slot` типа `varchar(20)` в виде строки `"18:00-19:30"`.

Проблемы текущего решения:

1. **Нет контроля пересечений.** Сравнить две строки как интервалы БД не может.
   Проверка выполняется только в коде сервиса и не защищена от гонки двух
   одновременных запросов — отсюда двойные бронирования одного зала.
2. **Грязные данные.** Разные клиенты (киоск, мобильное приложение, импорт из Excel)
   пишут разные форматы: `18.00 - 19.30`, `9:00-10:00`, встречаются некорректные
   значения (`весь день`, конец раньше начала).
3. **Нет аналитики.** Длительность занятий и загрузка залов по часам требуют
   разбора строки в каждом отчёте.

Ограничения: сервис должен работать без простоя; старые клиенты (мобильное
приложение 2.x, киоск) обновляются неделями и продолжат присылать `timeSlot`;
откат релиза должен оставаться возможным.

## Решение

1. Хранить слот как **диапазон времени PostgreSQL** — пользовательский
   диапазонный тип `sport.timerange` (`CREATE TYPE ... AS RANGE (subtype = time)`)
   с полуоткрытыми границами `[начало, конец)`: занятия `18:00–19:30` и
   `19:30–21:00` стыкуются без пересечения.
2. После переноса данных включить в БД **ограничение-исключение**
   `EXCLUDE USING gist (facility_id WITH =, booking_date WITH =, time_range WITH &&) WHERE (status = 'Active')`
   — пересекающиеся активные брони физически невозможны.
3. В коде ввести значимый тип `TimeRange` (C# `readonly record struct`) с разбором
   старого формата и преобразованием в литерал PostgreSQL.
4. Выполнять изменение по паттерну **Expand and Contract** в три фазы:

| Фаза | Скрипт | Что происходит | Совместимость |
|---|---|---|---|
| Expand | `01_expand.sql` | новая nullable-колонка `time_range`, триггер синхронизации | v1.8.x и v1.9.0 работают одновременно |
| Migrate | `02_migrate.sql` | пакетный перенос истории, журнал ошибок | сервис v1.9.0 пишет в обе колонки (dual write) |
| Contract | `03_contract.sql` | `NOT NULL`, удаление `time_slot` и триггера, EXCLUDE | только v1.9.x+, отдельный CR |

5. API — **аддитивное изменение контракта**: в ответ добавлено поле `timeRange`,
   поле `timeSlot` сохраняется до v2.0.0 с пометкой `Obsolete`; запрос принимает оба формата.
6. Фаза миграции переключается конфигурацией `BookingSchema:Phase` (`Expand` / `Contract`)
   без пересборки сервиса.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| Оставить строку + валидация регуляркой | минимум работы | пересечения по-прежнему не проверяются в БД, аналитика сложная | отклонён |
| Две колонки `start_time`, `end_time` | понятно любому, работает в любой СУБД | пересечения — сложное условие из четырёх сравнений, EXCLUDE требует выражения-диапазона, легко нарушить инвариант `end > start` | отклонён |
| `tsrange` с датой и временем | один столбец вместо `booking_date` + слот | ломает все запросы и отчёты по `booking_date`, большой объём изменений | отклонён (возможен в будущем) |
| JSONB `{ "start": ..., "end": ... }` | гибкость | нет типизации и индексации пересечений | отклонён |
| **Пользовательский `timerange` + EXCLUDE** | типизация, оператор `&&`, GiST-индекс, защита на уровне БД | специфично для PostgreSQL, нужен `btree_gist` | **принят** |

## Последствия

**Положительные**

* Двойные бронирования исключены на уровне БД, включая гонки запросов.
* Данные нормализованы: некорректный слот невозможно сохранить.
* Длительность и загрузка залов считаются функциями `lower()/upper()` без разбора строк.
* Каждый запрос оставляет цифровой след: тег `jira.issue=CAMPUS-110` и `campus.booking_id` в трассе.

**Отрицательные и риски**

* Решение привязано к PostgreSQL (тип RANGE, расширение `btree_gist`).
* На время перехода — избыточность (две колонки) и триггер, который нужно не забыть удалить в фазе Contract.
* Потребители, читающие `time_slot` напрямую из БД (BI-отчёты), должны перейти на `time_range` до фазы Contract — это Breaking Change для них (зафиксирован в CHANGELOG).
* После фазы Contract откат на v1.8.x возможен только восстановлением из резервной копии.

**Контроль выполнения**

* CI-проверка `db-migrations` прогоняет все три фазы на PostgreSQL 16 при каждом PR.
* Production sanity-тест после релиза проверяет создание брони в новом и старом формате.
* Фаза Contract — не ранее чем через 14 дней, отдельным CR-2026-118, при нулевом журнале ошибок миграции.
