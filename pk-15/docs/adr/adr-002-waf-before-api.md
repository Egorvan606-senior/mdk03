# ADR-002. WAF перед API: ModSecurity + OWASP CRS на Ingress NGINX

**Статус:** Утверждено.

**Дата:** 21.10.2026 · **Автор:** Иванов Е.М. · **Вариант 10, кейс 10**

## Контекст

На уровне прокси-сервера перед API разворачивается защита от DDoS-атак и SQL-инъекций.
Новый платёжный шлюз (ADR-001) требует, чтобы публичный API был закрыт WAF.
Главный риск кейса: **легитимные сложные JSON-запросы мобильного приложения** (вложенные
объекты, комментарии с кавычками и апострофами, слова *select*, *order by*) будут ошибочно
заблокированы правилами WAF, и покупатели не смогут оформить заказ.

## Решение

* WAF — **ModSecurity с правилами OWASP Core Rule Set** на существующем Ingress NGINX
  (без отдельного прокси — меньше точек отказа и задержек).
* Тело запроса разбирается как **JSON** (`ctl:requestBodyProcessor=JSON`): правила проверяют
  значения полей, а не сырой текст — это убирает основную массу ложных срабатываний.
* Уровень строгости CRS — **Paranoia Level 1**; лимит тела запроса 64 КБ; лимит частоты
  запросов 50 rps с одного IP (защита от DDoS на уровне L7).
* Ввод в два этапа: **7 дней `DetectionOnly`** (журнал + настройка исключений) → **`On`** в окне обслуживания.
* Поведение правил проверяется автотестами на учебном стенде `WafStandMiddleware`
  (smoke-тесты № 3–5).

## Последствия

* **Плюсы:** атаки SQL-инъекций и XSS блокируются до приложения; есть журнал атак;
  откат — смена режима на `DetectionOnly` за ≈ 10 секунд без отключения защиты от DDoS.
* **Минусы:** каждое новое поле или формат запроса мобильного приложения нужно проверять
  на ложные срабатывания до релиза; исключения правил (`ruleRemoveTargetById`) требуют
  ревью, иначе можно случайно открыть уязвимость.
