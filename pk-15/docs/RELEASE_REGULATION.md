## 0. Состав изменений и почему их два

Новый платёжный шлюз принимает трафик только от API, закрытого межсетевым экраном
веб-приложений (WAF): для публичных веб-приложений, обрабатывающих платёжные данные,
этого требует стандарт PCI DSS (требование 6.4). Поэтому релиз состоит из **двух
независимых изменений**, у каждого — свой smoke-тест и свой откат:

| № | Изменение | Что меняется | Откат |
|---|---|---|---|
| CH-1 | WAF перед API (кейс 10) | Ingress NGINX + ModSecurity + OWASP CRS: защита от SQL-инъекций, XSS, лимит размера тела и частоты запросов (DDoS) | перевод WAF в `DetectionOnly` (≈ 10 с) |
| CH-2 | Новый платёжный шлюз | `IPaymentService` → `NewGatewayPaymentService` (3-D Secure 2.0) | `kubectl rollout undo` (≤ 30 с) или `Payments__Provider=Legacy` |

Правило: CH-2 начинается **только после** успешных smoke-тестов CH-1. Так при сбое
сразу понятно, какое из изменений его вызвало.

Перед окном (T-7 дней) WAF уже работает на production в режиме **DetectionOnly**:
правила только журналируют срабатывания, а команда разбирает журнал и добавляет
исключения для легитимных запросов мобильного приложения. В окне режим меняется на `On`.

## 2. Smoke-тесты (дым-тесты) после деплоя

Автоматизированы в проекте `tests/OrderService.Tests` (`dotnet test --filter Category=Smoke`).

| № | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Запрос `GET /health` | статус **200**, `"status": "Healthy"`, `"version": "2.0.0"` |
| 2 | Проверка подключения к БД методом `DbContext.Database.CanConnect()` | `true` |
| 3 | `POST /api/v1/orders` со «сложным» JSON мобильного приложения (вложенные объекты, опции, апострофы, слова *select*, *order by* в комментарии) | **201**, WAF не заблокировал (нет ложного срабатывания) |
| 4 | Контрольная атака: `?search=1' OR '1'='1`, `UNION SELECT`, `<script>` | **403**, в ответе `ruleId` сработавшего правила |
| 5 | Заголовок `X-Waf-Mode` ответа | `On` |

Ручная проверка с консоли дежурного:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://orders.example.com/health          # ожидаем 200
curl -s -o /dev/null -w "%{http_code}\n" "https://orders.example.com/api/v1/orders/1?search=1'%20OR%20'1'='1"  # ожидаем 403
```

## 3. План отката (Rollback Plan)

**Условие активации отката (любое из):**

1. Доля ошибок **5xx превышает 3 %** в течение первых **3 минут** после переключения трафика.
2. (кейс 10) Доля ответов **403 от WAF на запросы мобильного приложения превышает 0,5 %** за 5 минут —
   признак того, что правила блокируют легитимных пользователей.
3. Не пройден любой smoke-тест из раздела 2.

**Технические действия:**

| Что откатываем | Команда | Время |
|---|---|---|
| CH-2 — сервис 2.0.0 | `kubectl rollout undo deployment/order-service -n production`<br>`kubectl rollout status deployment/order-service -n production` | до **30 секунд** |
| CH-2 — только платёжный шлюз (без пересборки) | `kubectl set env deployment/order-service Payments__Provider=Legacy -n production` | ≈ 30 секунд |
| CH-1 — WAF блокирует легитимные запросы | `kubectl apply -f deploy/k8s/order-service-ingress-waf-detection.yaml` (режим `DetectionOnly`: правила журналируют, но не блокируют) | ≈ 10 секунд |

WAF при откате **не выключается полностью**: режим `DetectionOnly` сохраняет журнал атак,
а защиту от DDoS (лимит частоты запросов) оставляет. Решение об откате принимает
ответственный за релиз; после отката — разбор (Post-Mortem) в течение 2 рабочих дней.
