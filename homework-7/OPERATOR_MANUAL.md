# Руководство оператора

**ИС «Умный кампус». АРМ оператора проходной и столовой**
Клиент Campus Operator 2.4.0 · утилита «Генератор ведомости питания» 1.0

Структура документа соответствует ГОСТ 19.505-79 «ЕСПД. Руководство оператора».

## 1. Назначение и условия применения программы

**Назначение.** Программа обеспечивает:

* контроль прохода через турникеты по электронным пропускам студентов и сотрудников;
* учёт оплаты питания в столовой по карте студента, в том числе льготного питания с дотацией;
* формирование отчётов: журнал проходов, загруженность аудиторий, ведомость питания.

**Условия применения.**

* АРМ прошло предпроектный аудит (docs/DEPLOYMENT_SCENARIO.md) и введено в эксплуатацию;
* Windows 10/11 x64, .NET 8, доступ к сети кампуса (TCP 443, 4317), считыватель на TCP 4001;
* оператор прошёл инструктаж и имеет доменную учётную запись с ролью «Оператор поста»
  или «Кассир столовой».

## 2. Подготовка к работе

### 2.1. Вход

1. Войдите в Windows под своей доменной учётной записью (не под общей!).
2. Запустите **Campus Operator** ярлыком на рабочем столе.
3. Дождитесь окна входа: имя пользователя подставится автоматически, нажмите **Войти**.

### 2.2. Выбор роли

| Роль | Кто | Доступные функции |
|---|---|---|
| Оператор поста | сотрудник охраны | проходы, ручной пропуск, журнал проходов |
| Кассир столовой | кассир | оплата питания, ведомость питания |
| Администратор АРМ | системный администратор | настройки, выгрузки, диагностика |

Выберите роль и пост (например, «Столовая, корпус А, касса 1») → **Начать смену**.
Проверьте строку состояния: «Сервер», «БД», «Считыватель» — зелёные.

## 3. Пошаговые сценарии работы (штатные операции)

### 3.1. Проход через турникет (роль «Оператор поста»)

1. Студент подносит карту к считывателю.
2. На экране — фото, ФИО, группа, статус пропуска.
3. Зелёная рамка — турникет открывается автоматически. Красная — проход запрещён, причина
   указана под фото; сверьте фото с владельцем, при необходимости — **Ручной проход** с указанием причины.

### 3.2. Оплата питания (роль «Кассир столовой»)

1. Выберите категорию: **Завтрак / Обед (комплекс) / Буфет / Ужин** и количество порций.
2. Студент прикладывает карту — программа показывает сумму, дотацию (для льготников) и сумму к оплате.
3. Нажмите **Провести**. Транзакция получает номер вида `TX-202610-00032`, печатается чек.
4. Оплата наличными — кнопка **Наличные**, номер карты вводится вручную.

### 3.3. Формирование ведомости питания за месяц

1. Меню **Отчёты → Ведомость питания** (или в командной строке АРМ:
   `campus-meal-statement --month 2026-10`).
2. Программа загрузит транзакции, сгруппирует их и сохранит в папку `statements`:

| Файл | Содержимое |
|---|---|
| `meal_transactions_2026-10.csv` | финансовый лог: каждая транзакция |
| `meal_statement_2026-10.csv` | ведомость по категориям питания с итогами |
| `meal_by_student_2026-10.csv` | суммы по каждому студенту и категории, дотации |
| `meal_statement_2026-10.sha256` | контрольные суммы файлов (защита от исправлений) |

3. Откройте CSV двойным щелчком — файл откроется в Excel с русскими буквами и запятой в суммах.
4. Передайте файлы в бухгалтерию **вместе с файлом `.sha256`**. Файлы не редактируются:
   любые правки делаются корректирующей транзакцией в программе.

## 4. Регламентные проверки и завершение смены

**В начале смены:** индикаторы зелёные; тестовая карта проходит; дата и время на АРМ верные;
в принтере есть бумага.

**В течение смены:** не реже раза в час проверяйте индикатор «Сервер»; при автономном режиме
сделайте отметку в бумажном журнале смены.

**Завершение смены:**

1. **Завершить смену** → программа синхронизирует журнал проходов/оплат с сервером.
2. Дождитесь сообщения «Журнал синхронизирован. Несинхронизированных записей: 0».
3. Кассир: сверьте итог смены на экране с Z-отчётом кассы.
4. Закройте программу и выйдите из Windows (**Win + L** недостаточно — выполните выход).

**Ежемесячно (до 3-го числа):** администратор формирует ведомость питания за прошлый месяц и
проверяет контрольные суммы: `Get-FileHash meal_statement_2026-10.csv -Algorithm SHA256`.

## 5. Аварийные ситуации и действия при сбоях (Troubleshooting)

| № | Признак | Возможная причина | Действия оператора |
|---|---|---|---|
| 1 | «Сервер» красный, надпись «Автономный режим» | нет связи с API кампуса | продолжайте работу: проходы и оплаты сохраняются локально. Сообщите в Service Desk (тел. 1234). После восстановления связи данные синхронизируются автоматически |
| 2 | «Считыватель не отвечает» | отключён кабель/питание контроллера | проверьте кабель и индикатор питания; проход — через **Ручной проход**, оплата — с вводом номера карты вручную; сообщите в Service Desk |
| 3 | Генератор ведомости: «Попытка N неудачна … Используется кэш» | API недоступен | ведомость сформирована по последней выгрузке и помечена «ПО ДАННЫМ КЭША». Не передавайте её в бухгалтерию как окончательную — повторите выгрузку после восстановления связи |
| 4 | «Файл … занят (открыт в Excel?) — сохраняю как …_HHmmss.csv» | прошлая ведомость открыта в Excel | закройте Excel; используйте новый файл с отметкой времени |
| 5 | «Источник данных недоступен, а кэша предыдущей выгрузки нет» | первая выгрузка без связи | дождитесь восстановления сети или запросите файл выгрузки у администратора (`--source <файл>`) |
| 6 | «Найдены дубликаты транзакций» | повторная выгрузка одних и тех же данных | ведомость не сформирована (защита от двойного учёта). Сообщите администратору номер транзакции из сообщения |
| 7 | «Нет прав на запись в папку ведомостей» | неверные права на папку | сообщите администратору; не запускайте программу «от имени администратора» |
| 8 | Программа не запускается после обновления | сбой обновления | администратор выполняет откат из резервной копии (UPDATE_GUIDE.md, ПР № 6) |
| 9 | Отключение электропитания | — | после включения дождитесь синхронизации, проверьте в журнале последние 5 записей |

В обращении в Service Desk указывайте номер АРМ, время, текст сообщения и приложите файл
журнала `statements\logs\meal_export_ГГГГММДД.log`.
